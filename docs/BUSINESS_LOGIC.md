# Business Logic

Этот документ нужен не для пользователя CRM, а для нового разработчика. Его цель — быстро объяснить бизнес-смысл основных сценариев, чтобы не собирать его по кускам из Prisma-схемы, UI и сервисов.

## Ключевые сущности

- `order` — верхний рабочий слой и реестр активных/закрытых сделок
- `rental` — сделка аренды велосипеда
- `buyout` — сделка выкупа велосипеда
- `payment_schedule` и `payment_schedule_items` — график плановых платежей
- `financial_transaction` — факт движения денег
- `penalty` — начисленный штраф
- `deposit` как отдельной сущности нет, но есть deal-level snapshot и finance rows по залогу
- `document_template` / `document` / `document_generation` — шаблоны и выпущенные документы

## Заказы и сделки

Экран заказов — это общий рабочий реестр.  
Из него менеджер уходит в конкретную карточку аренды или выкупа.

На сделке обычно сосредоточены:
- контекст клиента и велосипеда
- график платежей
- оплата
- документы
- штрафы
- залог
- заметки и операционные флаги

## Аренда

### Что важно по бизнесу

Аренда — это циклическая сделка с плановым платежом по тарифу:
- дневной;
- недельный;
- месячный.

У сделки есть:
- дата старта;
- тариф;
- плановый платеж;
- следующий платеж;
- долг;
- просрочка;
- льготные дни до автоштрафа;
- залог.

### График аренды

График аренды строится backend-логикой, а не UI:
- cadence выводится из длительности тарифа;
- schedule items получают статусы `PLANNED`, `PARTIAL`, `PAID`, `OVERDUE`;
- из графика пересчитываются `nextPaymentAt`, `debtKopecks`, `overdueDays`.

### Partial payments

Частичная оплата аренды допускается.  
Один платеж может:
- закрыть часть текущего цикла;
- изменить `paidKopecks` в schedule item;
- пересчитать долг, next payment и overdue snapshot.

### Продления и lifecycle

При изменении условий аренды backend может перестраивать график и статус сделки.  
Особенно аккуратно нужно относиться к:
- `HOLD`
- `RETURN_PREP`
- debt / overdue snapshot после schedule rebuild

## Выкуп

### Что важно по бизнесу

Выкуп — это сделка с общей ценой и графиком выплат:
- первый взнос;
- cadence `DAILY / WEEKLY / MONTHLY`;
- срок;
- остаток долга.

### График выкупа

График выкупа строится backend-логикой из:
- total price;
- down payment;
- cadence;
- term;
- preset logic для схем оплаты.

### Платежи выкупа

Платеж выкупа:
- отражается как finance fact;
- может частично закрывать schedule item;
- меняет residual debt;
- обновляет `nextPaymentAt` и `overdueDays`.

Переплата по графику выкупа ограничена, поэтому при изменениях здесь лучше сначала проверить текущие guard’ы в `finance/service.ts`.

## Unified Payment

Это один из самых чувствительных участков проекта.

`postUnifiedOrderPayment(...)` нужен, когда один денежный факт в карточке сделки раскладывается на:
- основную оплату по сделке;
- оплату одного или нескольких штрафов.

На уровне finance это не одна абстрактная сумма, а несколько записей `financial_transactions`, связанные общим `bundle/external reference`.

Из-за этого важно помнить:
- один платеж в UI может порождать несколько money rows;
- reversal и audit нужно рассматривать на уровне каждой finance row;
- bundle-связь нужна для чтения истории и сверки.

## Штрафы

### Начисление

Штраф — это отдельная доменная сущность, а не просто комментарий к платежу.

Есть:
- ручное начисление;
- auto-run / auto penalty сценарии;
- статус активного штрафа;
- связь штрафа со сделкой.

### Оплата

Оплата штрафа — это отдельный денежный факт.  
Начисление и оплата не должны смешиваться.

Для разработчика это означает:
- UI начисления и UI оплаты живут рядом, но это разные операции;
- finance row по оплате штрафа не равна самой penalty-сущности;
- unified payment может оплачивать штраф вместе с основной суммой сделки.

## Залоги

### Прием

Прием залога — отдельный факт прихода денег, связанный со сделкой.  
Он влияет на snapshot сделки:
- target;
- collected;
- returned;
- available to refund.

### Возврат

Возврат залога — отдельный факт расхода денег.  
Важно различать:
- наличные;
- перевод;
- какой банк использован при возврате.

### Что важно для разработчика

- collect и refund залога — это разные finance operations;
- состояние залога на карточке — это не только UI, а результат агрегирования денег по сделке;
- возврат залога сильно завязан на выбранный банк и payment method.

## Документы

### Что живет в `/documents`

`/documents` — это authoring-экран:
- список шаблонов;
- editor-first рабочая зона;
- коды CRM/placeholders;
- архив выпущенных документов.

### Что живет в карточке сделки

Карточка сделки — это issue flow:
- выбрать шаблон;
- выпустить документ;
- открыть;
- скачать;
- печать.

То есть:
- `/documents` = работа с шаблонами
- карточка сделки = выпуск документа по конкретной сделке

### Шаблоны и коды

Поддерживаются шаблоны:
- `.txt`
- `.docx`

Коды подставляются в формате `{{...}}`.  
Каталог кодов зависит от `sourceEntityType`:
- `CLIENT`
- `RENTAL`
- `BUYOUT`

### Ограничения `.txt` и `.docx`

- `.txt` можно безопасно читать, редактировать и preview’ить прямо в CRM
- `.docx` идет через safe-flow на backend и имеет ограничения Word XML
- DOCX placeholders могут быть разорваны Word на XML-runs, поэтому preview/generate для них нужно считать safe, но не абсолютным

Это одна из причин, почему document preview и generate нельзя рефакторить как “просто текстовый редактор”.

## Финансы

Раздел `/finance` — это рабочий реестр денег, а не бухгалтерия и не BI.

### Что такое финансовая строка

Операция должна читаться по слоям:
- приход или расход;
- контур денег;
- статья;
- клиент;
- заказ;
- банк / способ;
- комментарий и статус.

### Контур денег

В UI важен не raw `transaction type`, а бизнес-контур:
- аренда
- выкуп
- штраф
- залог
- расход бизнеса

Raw type остается в модели, но UI показывает operator-facing label.

### Business contour и статьи

Примеры нормальных статей:
- `Оплата аренды`
- `Частичная оплата аренды`
- `Оплата выкупа`
- `Частичный платеж выкупа`
- `Оплата штрафа`
- `Принят залог`
- `Возврат залога`
- `Ремонт`
- `Логистика`
- `Административные`

### Bundle / external reference

Один реальный платеж может быть разложен на несколько `financial_transactions`.  
Связь между ними держится через bundle/external reference.

Это важно для:
- unified payment;
- сверки;
- reverse/correction flow;
- чтения истории сделки в finance registry.

## Partial payments, debt, overdue

Это одна из самых чувствительных логик системы.

Важно помнить:
- долг считается из графика, а не только из последнего платежа;
- просрочка считается по due-date и outstanding amount;
- partial payment не закрывает цикл автоматически, если outstanding еще есть;
- rebuild schedule может пересчитать deal snapshot даже без прямого изменения UI.

## Ключевые статусы и смысл

### Для графика

- `PLANNED` — платеж запланирован
- `PARTIAL` — есть частичная оплата
- `PAID` — цикл закрыт
- `OVERDUE` — due-date уже прошел, а outstanding еще есть

### Для аренды и выкупа

В коде встречаются, например:
- `NEW`
- `ACTIVE`
- `OVERDUE`
- `HOLD`
- `RETURN_PREP`
- закрывающие статусы по домену

Именно статусы сделки, графика и finance rows нужно читать вместе, а не по отдельности.
